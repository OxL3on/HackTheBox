# Domain Name System (DNS) - [LINK](https://academy.hackthebox.com/app/module/112/section/1069)

## Introduction (ভূমিকা)

**Domain Name System (DNS)** ইন্টারনেটের একটি অবিচ্ছেদ্য অংশ। উদাহরণস্বরূপ, `academy.hackthebox.com` বা `[www.hackthebox.com](https://www.hackthebox.com)`-এর মতো ডোমেইন নামগুলোর মাধ্যমে আমরা সেই ওয়েব সার্ভারগুলোতে পৌঁছাতে পারি, যেগুলোর জন্য হোস্টিং প্রোভাইডার এক বা একাধিক নির্দিষ্ট IP address অ্যাসাইন করেছে।

DNS মূলত কম্পিউটারের নামকে IP address-এ রূপান্তর (resolve) করার একটি সিস্টেম। এর নিজস্ব কোনো কেন্দ্রীয় ডাটাবেস (central database) নেই। সহজ ভাষায়, আমরা এটিকে এমন একটি লাইব্রেরি হিসেবে কল্পনা করতে পারি যেখানে অসংখ্য ভিন্ন ভিন্ন ফোনবুক রয়েছে। এর তথ্যগুলো বিশ্বজুড়ে থাকা হাজার হাজার নেম সার্ভারের (name servers) মধ্যে ডিস্ট্রিবিউট করা থাকে। বিশ্বব্যাপী বিস্তৃত এই DNS সার্ভারগুলো ডোমেইন নামকে IP address-এ ট্রান্সলেট করে এবং নির্দিষ্ট ডোমেইনের মাধ্যমে ইউজার কোন সার্ভারে পৌঁছাবে তা নিয়ন্ত্রণ করে।

বিশ্বব্যাপী বিভিন্ন ধরনের DNS সার্ভার ব্যবহৃত হয়:

| Server Type | Description (বিবরণ) |
| --- | --- |
| **DNS Root Server** | DNS-এর root server-গুলো top-level domains (TLD)-এর জন্য দায়ী। সর্বশেষ বিকল্প হিসেবে শুধুমাত্র তখনই এদের কাছে রিকোয়েস্ট করা হয়, যখন কোনো নেম সার্ভার রেসপন্স করে না। Root server মূলত ইন্টারনেট ইউজার এবং কন্টেন্টের মধ্যে একটি সেন্ট্রাল ইন্টারফেস হিসেবে কাজ করে, কারণ এটি ডোমেইন এবং IP address-কে লিংক করে। ICANN (Internet Corporation for Assigned Names and Numbers) এই root name server-গুলোর কাজ সমন্বয় করে। বিশ্বজুড়ে এ ধরনের ১৩টি root server রয়েছে। |
| **Authoritative Nameserver** | এই সার্ভারগুলো একটি নির্দিষ্ট জোনের (zone) জন্য অথরিটি ধারণ করে। এরা শুধুমাত্র নিজেদের দায়িত্বপ্রাপ্ত এলাকার (area of responsibility) কোয়েরির উত্তর দেয় এবং এদের দেওয়া তথ্য বাধ্যতামূলক (binding)। যদি কোনো Authoritative nameserver ক্লায়েন্টের কোয়েরির উত্তর দিতে না পারে, তখন root name server সেই দায়িত্ব নেয়। দেশ, কোম্পানি ইত্যাদির ওপর ভিত্তি করে Authoritative nameserver-গুলো recursive DNS nameserver-কে উত্তর প্রদান করে, যা নির্দিষ্ট ওয়েব সার্ভার খুঁজে পেতে সাহায্য করে। |
| **Non-authoritative Nameserver** | এরা কোনো নির্দিষ্ট DNS zone-এর জন্য দায়ী নয়। এর বদলে এরা নিজেরাই recursive বা iterative DNS query ব্যবহার করে নির্দিষ্ট DNS zone সম্পর্কে তথ্য সংগ্রহ করে। |
| **Caching DNS Server** | এই সার্ভারগুলো একটি নির্দিষ্ট সময়ের জন্য অন্যান্য নেম সার্ভার থেকে প্রাপ্ত তথ্য ক্যাশ (cache) করে রাখে। Authoritative name server এই ক্যাশ স্টোরেজের সময়কাল নির্ধারণ করে দেয়। |
| **Forwarding Server** | এরা শুধুমাত্র একটি কাজ করে: এরা DNS কোয়েরিগুলো অন্য কোনো DNS সার্ভারে ফরোয়ার্ড করে দেয়। |
| **Resolver** | Resolver-রা authoritative DNS server নয়, তবে এরা কম্পিউটার বা রাউটারে লোকালি নেম রেজোলিউশন (name resolution) সম্পন্ন করে। |

### DNS Encryption (DNS এনক্রিপশন)

DNS ডিফল্টভাবে **unencrypted** থাকে। ফলে লোকাল WLAN-এর ডিভাইস এবং ইন্টারনেট প্রোভাইডাররা সহজেই DNS কোয়েরিগুলো স্পাই (spy) বা হ্যাক করতে পারে। এটি একটি বড় প্রাইভেসি রিস্ক তৈরি করে বলে বর্তমানে DNS এনক্রিপশনের কিছু সলিউশন রয়েছে। IT সিকিউরিটি প্রফেশনালরা সাধারণত **DNS over TLS (DoT)** বা **DNS over HTTPS (DoH)** ব্যবহার করেন। এছাড়া, **DNSCrypt** নেটওয়ার্ক প্রোটোকলও কম্পিউটার এবং নেম সার্ভারের মধ্যকার ট্রাফিক এনক্রিপ্ট করে।

## DNS Records

DNS শুধুমাত্র কম্পিউটার নাম এবং IP address লিংক করে না। এটি একটি ডোমেইনের সাথে যুক্ত সার্ভিসগুলো সম্পর্কে অতিরিক্ত তথ্য স্টোর করে এবং আউটপুট দেয়। একটি DNS কোয়েরি ব্যবহার করে বের করা সম্ভব কোন কম্পিউটারটি ওই ডোমেইনের e-mail server হিসেবে কাজ করছে বা ডোমেইনের নেম সার্ভারগুলোর নাম কী।

DNS কোয়েরির জন্য বিভিন্ন ধরনের DNS records ব্যবহৃত হয়, যাদের কাজ ভিন্ন ভিন্ন:

| DNS Record | Description (বিবরণ) |
| --- | --- |
| **A** | রিকোয়েস্ট করা ডোমেইনের একটি IPv4 অ্যাড্রেস রিটার্ন করে। |
| **AAAA** | রিকোয়েস্ট করা ডোমেইনের একটি IPv6 অ্যাড্রেস রিটার্ন করে। |
| **MX** | ডোমেইনের জন্য রেসপন্সিবল mail server রিটার্ন করে। |
| **NS** | ডোমেইনের DNS servers (nameservers) রিটার্ন করে। |
| **TXT** | এই রেকর্ডে বিভিন্ন ধরনের তথ্য থাকতে পারে। এটি বহুমুখী (all-rounder) রেকর্ড যা Google Search Console বা SSL সার্টিফিকেট ভ্যালিডেট করতে ব্যবহৃত হয়। এছাড়া মেইল ট্রাফিক ভ্যালিডেট এবং স্প্যাম থেকে রক্ষা করার জন্য SPF এবং DMARC এন্ট্রি সেট করতে এটি ব্যবহৃত হয়। |
| **CNAME** | এই রেকর্ডটি অন্য একটি ডোমেইন নামের alias (উপনাম) হিসেবে কাজ করে। যদি আপনি চান `www.hackthebox.eu` এবং `hackthebox.eu` একই IP-কে পয়েন্ট করুক, তবে `hackthebox.eu`-এর জন্য একটি A রেকর্ড এবং `www.hackthebox.eu`-এর জন্য একটি CNAME রেকর্ড তৈরি করতে হবে। |
| **PTR** | PTR রেকর্ড ঠিক উল্টোভাবে কাজ করে (reverse lookup)। এটি IP অ্যাড্রেসকে ভ্যালিড ডোমেইন নামে কনভার্ট করে। |
| **SOA** | এটি সংশ্লিষ্ট DNS zone এবং অ্যাডমিনিস্ট্রেটিভ কন্টাক্টের (administrative contact) ইমেইল অ্যাড্রেস সম্পর্কে তথ্য প্রদান করে। |

### SOA Record Example

SOA (Start of Authority) রেকর্ডটি একটি ডোমেইনের জোন ফাইলে (zone file) অবস্থিত থাকে এবং নির্দেশ করে কে এই ডোমেইনটি পরিচালনার দায়িত্বে আছে এবং ডোমেইনটির DNS তথ্য কীভাবে পরিচালিত হচ্ছে।

```bash
00Luffy00@htb[/htb]$ dig soa www.inlanefreight.com

; <<>> DiG 9.16.27-Debian <<>> soa www.inlanefreight.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 15876
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 512
;; QUESTION SECTION:
;www.inlanefreight.com.         IN      SOA

;; AUTHORITY SECTION:
inlanefreight.com.      900     IN      SOA     ns-161.awsdns-20.com. awsdns-hostmaster.amazon.com. 1 7200 900 1209600 86400

;; Query time: 16 msec
;; SERVER: 8.8.8.8#53(8.8.8.8)
;; WHEN: Thu Jan 05 12:56:10 GMT 2023
;; MSG SIZE  rcvd: 128

```

> **Important Note:** SOA রেকর্ডে ইমেইল অ্যাড্রেসের `@` (at sign) চিহ্নের পরিবর্তে একটি `.` (dot) ব্যবহার করা হয়। উপরের উদাহরণে অ্যাডমিনিস্ট্রেটরের ইমেইল অ্যাড্রেসটি হলো: `awsdns-hostmaster@amazon.com`।

## Default Configuration (ডিফল্ট কনফিগারেশন)

DNS-এর জন্য অনেক ধরনের কনফিগারেশন রয়েছে। অ্যাডমিনিস্ট্রেটিভ দৃষ্টিকোণ থেকে ফাংশনাল প্রিন্সিপালগুলো বোঝার জন্য সবচেয়ে গুরুত্বপূর্ণ বিষয়গুলো নিয়ে নিচে আলোচনা করা হলো। সমস্ত DNS সার্ভার মূলত তিনটি ভিন্ন ধরনের কনফিগারেশন ফাইল নিয়ে কাজ করে:

1. **local DNS configuration files**
2. **zone files**
3. **reverse name resolution files**

Linux-ভিত্তিক ডিস্ট্রিবিউশনগুলোতে **Bind9** নামক DNS সার্ভারটি সবচেয়ে বেশি ব্যবহৃত হয়। এর লোকাল কনফিগারেশন ফাইলটি (`named.conf`) মূলত দুটি অংশে বিভক্ত থাকে:

* **Options section:** সাধারণ সেটিংসের জন্য।
* **Zone entries:** বিভিন্ন ডোমেইনের জন্য।

লোকাল কনফিগারেশন ফাইলগুলো সাধারণত নিচের মতো হয়:

* `named.conf.local`
* `named.conf.options`
* `named.conf.log`

`named.conf` ফাইলটি কয়েকটি options-এ বিভক্ত থাকে, যা নেম সার্ভারের আচরণ নিয়ন্ত্রণ করে। এখানে **Global options** (যা সব জোনের ওপর প্রভাব ফেলে) এবং **Zone options** (যা শুধুমাত্র নির্দিষ্ট জোনের ওপর প্রভাব ফেলে)-এর মধ্যে পার্থক্য করা হয়। যদি কোনো অপশন গ্লোবাল এবং জোন—উভয় জায়গাতেই থাকে, তবে **zone option-টি অগ্রাধিকার (precedence) পায়**।

### Local DNS Configuration

```bash
root@bind9:~# cat /etc/bind/named.conf.local

//
// Do any local configuration here
//

// Consider adding the 1918 zones here, if they are not used in your
// organization
//include "/etc/bind/zones.rfc1918";
zone "domain.com" {
    type master;
    file "/etc/bind/db.domain.com";
    allow-update { key rndc-key; };
};

```

এই ফাইলে আমরা বিভিন্ন জোন ডিফাইন করতে পারি। এই জোনগুলো আলাদা আলাদা ফাইলে বিভক্ত থাকে, যা বেশিরভাগ ক্ষেত্রেই কেবল একটি ডোমেইনের জন্য নির্ধারিত।

### Zone Files

Zone file হলো একটি টেক্সট ফাইল যা BIND ফাইল ফরম্যাটে একটি DNS জোনকে বর্ণনা করে। সহজ কথায়, এটি DNS ট্রি-এর (tree) একটি ডেলিগেশন পয়েন্ট। একটি জোন ফাইলে অবশ্যই ঠিক একটি **SOA রেকর্ড** এবং অন্তত একটি **NS রেকর্ড** থাকতে হবে।

যদি ফাইলে কোনো syntax error থাকে, তবে সম্পূর্ণ জোন ফাইলটিকে অকেজো (unusable) হিসেবে বিবেচনা করা হয়। নেম সার্ভার এমনভাবে আচরণ করে যেন এই জোনটির কোনো অস্তিত্বই নেই এবং এটি DNS কোয়েরির রেসপন্সে **SERVFAIL** এরর মেসেজ পাঠায়।

```bash
root@bind9:~# cat /etc/bind/db.domain.com

;
; BIND reverse data file for local loopback interface
;
$ORIGIN domain.com
$TTL 86400
@     IN     SOA    dns1.domain.com.     hostmaster.domain.com. (
                    2001062501 ; serial
                    21600      ; refresh after 6 hours
                    3600       ; retry after 1 hour
                    604800     ; expire after 1 week
                    86400 )    ; minimum TTL of 1 day

      IN     NS     ns1.domain.com.
      IN     NS     ns2.domain.com.

      IN     MX     10     mx.domain.com.
      IN     MX     20     mx2.domain.com.

             IN     A       10.129.14.5

server1      IN     A       10.129.14.5
server2      IN     A       10.129.14.7
ns1          IN     A       10.129.14.2
ns2          IN     A       10.129.14.3

ftp          IN     CNAME   server1
mx           IN     CNAME   server1
mx2          IN     CNAME   server2
www          IN     CNAME   server2

```

### Reverse Name Resolution Zone Files

IP অ্যাড্রেস থেকে FQDN (Fully Qualified Domain Name) রিজলভ করার জন্য DNS সার্ভারে একটি reverse lookup file থাকতে হয়। এই ফাইলে PTR রেকর্ড ব্যবহার করে একটি IP অ্যাড্রেসের শেষ অক্টেটের সাথে কম্পিউটারের নাম (FQDN) অ্যাসাইন করা হয়।

```bash
root@bind9:~# cat /etc/bind/db.10.129.14

;
; BIND reverse data file for local loopback interface
;
$ORIGIN 14.129.10.in-addr.arpa
$TTL 86400
@     IN     SOA    dns1.domain.com.     hostmaster.domain.com. (
                    2001062501 ; serial
                    21600      ; refresh after 6 hours
                    3600       ; retry after 1 hour
```

## Dangerous Settings (ঝুঁকিপূর্ণ কনফিগারেশন)

একটি DNS সার্ভারকে বিভিন্ন উপায়ে আক্রমণ (attack) করা যেতে পারে। BIND9 সার্ভারকে টার্গেট করা ভালনারেবিলিটির তালিকা **CVEdetails** এবং **SecurityTrails**-এ পাওয়া যায়।
DNS অনেক জটিল হতে পারে এবং এতে সহজেই ভুল ঢুকে যেতে পারে। অ্যাডমিনিস্ট্রেটররা অনেক সময় ইনফ্রাস্ট্রাকচার সচল রাখার জন্য সিকিউরিটির চেয়ে ফাংশনালিটিকে (functionality) বেশি অগ্রাধিকার দেন, যা misconfigurations এবং vulnerabilities তৈরি করে।

নিচে এমন কিছু অপশন দেওয়া হলো যা ঝুঁকিপূর্ণ হতে পারে:

| Option | Description (বিবরণ) |
| --- | --- |
| `allow-query` | কোন হোস্টগুলো DNS সার্ভারে রিকোয়েস্ট পাঠাতে পারবে তা নির্ধারণ করে। |
| `allow-recursion` | কোন হোস্টগুলো DNS সার্ভারে recursive রিকোয়েস্ট পাঠাতে পারবে তা নির্ধারণ করে। |
| `allow-transfer` | কোন হোস্টগুলো DNS সার্ভার থেকে zone transfers গ্রহণ করতে পারবে তা নির্ধারণ করে। |
| `zone-statistics` | জোনগুলোর স্ট্যাটিস্টিক্যাল ডেটা সংগ্রহ করে। |

## Footprinting the Service (সার্ভিস ফুটপ্রিন্টিং)

আমরা DNS সার্ভারে বিভিন্ন রিকোয়েস্ট পাঠানোর মাধ্যমে ফুটপ্রিন্টিং সম্পন্ন করতে পারি।

### 1. NS Query

প্রথমে আমরা DNS সার্ভারকে কোয়েরি করতে পারি যে এটি অন্য কোনো নেম সার্ভার সম্পর্কে জানে কিনা। এর জন্য আমরা NS রেকর্ড ব্যবহার করি এবং `@` ক্যারেক্টার দিয়ে যে DNS সার্ভারটিকে কোয়েরি করতে চাই তা নির্দিষ্ট করে দিই।

```bash
00Luffy00@htb[/htb]$ dig ns inlanefreight.htb @10.129.14.128

; <<>> DiG 9.16.1-Ubuntu <<>> ns inlanefreight.htb @10.129.14.128
;; global options: +cmd
;; Got answer:
...
;; ANSWER SECTION:
inlanefreight.htb.      604800  IN      NS      ns.inlanefreight.htb.

;; ADDITIONAL SECTION:
ns.inlanefreight.htb.   604800  IN      A       10.129.34.136
...

```

### 2. Version Query (Bind Version)

কখনো কখনো `CHAOS` ক্লাস এবং `TXT` টাইপ কোয়েরি ব্যবহার করে DNS সার্ভারের ভার্সন বের করা সম্ভব (যদি এই এন্ট্রি সার্ভারে থেকে থাকে)।

```bash
00Luffy00@htb[/htb]$ dig CH TXT version.bind 10.129.120.85

; <<>> DiG 9.10.6 <<>> CH TXT version.bind
;; global options: +cmd
;; Got answer:
...
;; ANSWER SECTION:
version.bind.       0       CH      TXT     "9.10.6-P1"

;; ADDITIONAL SECTION:
version.bind.       0       CH      TXT     "9.10.6-P1-Debian"
...

```

### 3. ANY Query

আমরা `ANY` অপশন ব্যবহার করে সার্ভারের সমস্ত অ্যাভেইলেবল রেকর্ড দেখার জন্য রিকোয়েস্ট পাঠাতে পারি। সার্ভার যে রেকর্ডগুলো প্রকাশ করতে ইচ্ছুক, শুধুমাত্র সেগুলোই দেখাবে। **নোট:** জোন থেকে সব এন্ট্রি এখানে দেখানো নাও হতে পারে।


## Zone Transfer (AXFR)

Zone transfer বলতে DNS-এর একটি জোনকে অন্য কোনো সার্ভারে ট্রান্সফার করা বোঝায়, যা সাধারণত **TCP port 53**-এর মাধ্যমে ঘটে। এই প্রক্রিয়াটিকে সংক্ষেপে **AXFR (Asynchronous Full Transfer Zone)** বলা হয়।

যেহেতু একটি DNS ফেইলর কোম্পানির জন্য মারাত্মক পরিণতি ডেকে আনতে পারে, তাই জোন ফাইলটি সবসময় একাধিক নেম সার্ভারে হুবহু এক রাখা হয়। সার্ভারগুলোর মধ্যে সিঙ্ক্রোনাইজেশন করার জন্যই Zone transfer ব্যবহার করা হয়। সার্ভারগুলো `rndc-key` নামক একটি সিক্রেট কী (secret key) ব্যবহার করে নিশ্চিত হয় যে তারা তাদের নিজস্ব master বা slave-এর সাথেই যোগাযোগ করছে।

* **Primary/Master:** যে DNS সার্ভারে কোনো জোনের অরিজিনাল ডেটা থাকে।
* **Secondary/Slave:** প্রাইমারির ওপর লোড কমাতে বা নিরাপত্তা বাড়াতে যে অতিরিক্ত সার্ভারগুলো ব্যবহার করা হয়।

Slave নির্দিষ্ট সময় পরপর (refresh time, সাধারণত ১ ঘণ্টা) Master থেকে SOA রেকর্ড ফেচ (fetch) করে এবং তাদের **serial numbers** তুলনা করে। Master-এর সিরিয়াল নম্বর Slave-এর চেয়ে বড় হলে সার্ভার বুঝতে পারে যে ডেটা আপডেট করা প্রয়োজন।

### DIG - AXFR Zone Transfer


যদি অ্যাডমিনিস্ট্রেটর টেস্টিংয়ের জন্য `allow-transfer` অপশনটিতে কোনো সাবনেট বা `any` সেট করে রাখেন, তবে যে কেউই DNS সার্ভার থেকে সম্পূর্ণ জোন ফাইল কোয়েরি করতে পারবে। এর মাধ্যমে অনেক ইন্টারনাল IP অ্যাড্রেস এবং হোস্টনেম ফাঁস হয়ে যেতে পারে।

## Subdomain Brute Forcing

যদি Zone Transfer রেস্ট্রিক্টেড থাকে, তবে আমরা ব্রুট-ফোর্স (brute-force) অ্যাটাকের মাধ্যমে বিভিন্ন হোস্টনেম (A records) খুঁজে বের করতে পারি। এর জন্য আমাদের সম্ভাব্য হোস্টনেমগুলোর একটি লিস্ট প্রয়োজন হবে, যা ব্যবহার করে আমরা একে একে রিকোয়েস্ট পাঠাব। এ ধরনের লিস্ট **SecLists**-এ পাওয়া যায়।

আমরা Bash-এ একটি `for-loop` ব্যবহার করে এই লিস্ট থেকে ডোমেইনগুলো চেক করতে পারি:

```bash
00Luffy00@htb[/htb]$ for sub in $(cat /opt/useful/seclists/Discovery/DNS/subdomains-top1million-110000.txt);do dig $sub.inlanefreight.htb @10.129.14.128 | grep -v ';\|SOA' | sed -r '/^\s*$/d' | grep $sub | tee -a subdomains.txt;done

ns.inlanefreight.htb.   604800  IN      A       10.129.34.136
mail1.inlanefreight.htb. 604800 IN      A       10.129.18.201
app.inlanefreight.htb.  604800  IN      A       10.129.18.15

```
