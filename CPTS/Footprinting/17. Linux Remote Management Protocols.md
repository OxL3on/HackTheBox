## Introduction (ভূমিকা)

Linux ডিস্ট্রিবিউশনের জগতে রিমোটলি সার্ভার ম্যানেজ করার অনেক উপায় রয়েছে। পাবলিক নেটওয়ার্কে থাকা প্রায় প্রতিটি সার্ভারেই এই অ্যাপ্লিকেশন এবং সার্ভিসগুলো পাওয়া যায়। এগুলোর মাধ্যমে ফিজিক্যালি সার্ভারের কাছে উপস্থিত না থেকেই কাজ করা যায় বলে এটি অনেক সময় বাঁচায়, এবং কাজের পরিবেশও ঠিক একই রকম থাকে।

রিমোট সিস্টেম ম্যানেজমেন্টের জন্য ব্যবহৃত এই প্রোটোকল এবং অ্যাপ্লিকেশনগুলো পেনিট্রেশন টেস্টারদের জন্য অত্যন্ত আকর্ষণীয় একটি লক্ষ্য (target)। যদি এগুলোর কনফিগারেশনে কোনো ত্রুটি (misconfiguration) থাকে, তবে আমরা খুব সহজেই রিমোট সিস্টেমের অ্যাক্সেস পেয়ে যেতে পারি। এ কারণে আমাদের সবচেয়ে গুরুত্বপূর্ণ প্রোটোকল, সার্ভার এবং অ্যাপ্লিকেশনগুলোর সাথে পরিচিত হওয়া প্রয়োজন।

## SSH (Secure Shell)

**Secure Shell (SSH)** দুটি কম্পিউটারের মধ্যে একটি সম্ভাব্য অনিরাপদ (insecure) নেটওয়ার্কেও স্ট্যান্ডার্ড **TCP port 22** ব্যবহার করে একটি এনক্রিপ্টেড এবং ডিরেক্ট কানেকশন স্থাপন করতে সক্ষম। তৃতীয় কোনো পক্ষ (third party) যেন ডেটা স্ট্রিম এবং সংবেদনশীল (sensitive) ডেটা ইন্টারসেপ্ট (intercept) করতে না পারে, সেজন্য এটি প্রয়োজনীয়।

SSH সার্ভারকে এমনভাবে কনফিগার করা যায় যাতে এটি শুধুমাত্র নির্দিষ্ট ক্লায়েন্টদের থেকেই কানেকশন গ্রহণ করে। SSH-এর একটি বড় সুবিধা হলো এই প্রোটোকলটি সব সাধারণ অপারেটিং সিস্টেমেই কাজ করে। যেহেতু এটি মূলত একটি Unix অ্যাপ্লিকেশন, তাই এটি সমস্ত Linux ডিস্ট্রিবিউশন এবং MacOS-এ নেটিভলি ইমপ্লিমেন্ট করা থাকে। প্রয়োজনীয় প্রোগ্রাম ইন্সটল করে Windows-এও SSH ব্যবহার করা যায়।

Linux ডিস্ট্রিবিউশনে থাকা সুপরিচিত **OpenBSD SSH (OpenSSH)** সার্ভারটি মূলত SSH Communication Security-এর তৈরি অরিজিনাল এবং কমার্শিয়াল SSH সার্ভারের একটি ওপেন-সোর্স ফর্ক (fork)। এর দুটি প্রতিযোগী প্রোটোকল রয়েছে: **SSH-1** এবং **SSH-2**।

**SSH-2 (SSH version 2)** হলো SSH version 1-এর চেয়ে বেশি উন্নত একটি প্রোটোকল, যা এনক্রিপশন, স্পিড, স্ট্যাবিলিটি এবং সিকিউরিটির দিক থেকে অনেক এগিয়ে। উদাহরণস্বরূপ, SSH-1 **MITM (Man-In-The-Middle)** অ্যাটাকের প্রতি ভালনারেবল হলেও SSH-2 নয়।

SSH প্রোটোকল ব্যবহার করে আমরা রিমোট সিস্টেমে কমান্ড পাঠাতে, ফাইল ট্রান্সফার করতে বা পোর্ট ফরোয়ার্ডিং করতে পারি। ഇതിন জন্য আমাদের SSH প্রোটোকল ব্যবহার করে কানেক্ট করতে হবে এবং নিজেদের অথেনটিকেট (authenticate) করতে হবে। OpenSSH-এ মোট ছয় ধরনের অথেনটিকেশন মেথড রয়েছে:

1. Password authentication
2. Public-key authentication
3. Host-based authentication
4. Keyboard authentication
5. Challenge-response authentication
6. GSSAPI authentication

### Public Key Authentication

প্রথম ধাপে, SSH সার্ভার এবং ক্লায়েন্ট একে অপরের কাছে নিজেদের অথেনটিকেট করে। সার্ভার তার পাবলিক হোস্ট কী (public host key) ক্লায়েন্টকে পাঠায়, যা ব্যবহার করে ক্লায়েন্ট সার্ভারের আইডেন্টিটি ভেরিফাই করে।
সার্ভার অথেনটিকেশনের পর, ক্লায়েন্টকেও প্রমাণ করতে হয় যে তার অ্যাক্সেস অথোরাইজেশন আছে। ইউজারদের বারবার পাসওয়ার্ড টাইপ করার ঝামেলা এড়াতে ক্লায়েন্ট-সাইড অথেনটিকেশনের জন্য **public key এবং private key pair** ব্যবহার করা হয়।

* **Private Key:** এটি ইউজারের নিজের কম্পিউটারের জন্য তৈরি করা হয় এবং একটি `passphrase` দিয়ে সুরক্ষিত থাকে। এটি শুধুমাত্র ইউজারের কম্পিউটারে স্টোর করা থাকে এবং সব সময় গোপন থাকে।
* **Public Key:** এটি সার্ভারে স্টোর করা থাকে। সার্ভার ক্লায়েন্টের পাবলিক কী ব্যবহার করে একটি ক্রিপ্টোগ্রাফিক প্রবলেম তৈরি করে ক্লায়েন্টকে পাঠায়। ক্লায়েন্ট তার নিজস্ব প্রাইভেট কী দিয়ে সেটি ডিক্রিপ্ট করে সমাধানটি (solution) সার্ভারকে ফেরত পাঠায় এবং প্রমাণ করে যে তার কানেকশনটি লেজিটিমেট (legitimate)।

### Default Configuration

OpenSSH সার্ভারের জন্য দায়ী কনফিগারেশন ফাইলটি হলো `sshd_config`। এর ডিফল্ট কনফিগারেশনে **X11 forwarding** যুক্ত থাকে, যা ২০১৬ সালে OpenSSH-এর 7.2p1 ভার্সনে একটি command injection ভালনারেবিলিটির কারণ হয়েছিল। (আমাদের সার্ভার ম্যানেজ করার জন্য GUI-এর কোনো প্রয়োজন নেই)।

```bash
00Luffy00@htb[/htb]$ cat /etc/ssh/sshd_config  | grep -v "#" | sed -r '/^\s*$/d'

Include /etc/ssh/sshd_config.d/*.conf
ChallengeResponseAuthentication no
UsePAM yes
X11Forwarding yes
PrintMotd no
AcceptEnv LANG LC_*
Subsystem       sftp    /usr/lib/openssh/sftp-server

```

এই কনফিগারেশন ফাইলের বেশিরভাগ সেটিংস কমেন্ট আউট (commented out) করা থাকে এবং ম্যানুয়াল কনফিগারেশনের প্রয়োজন হয়।

### Dangerous Settings (ঝুঁকিপূর্ণ সেটিংস)

SSH প্রোটোকল নিরাপদ হওয়া সত্ত্বেও কিছু ভুল কনফিগারেশনের কারণে এটি অ্যাটাকের শিকার হতে পারে।

| Setting | Description (বিবরণ) |
| --- | --- |
| `PasswordAuthentication yes` | পাসওয়ার্ড-ভিত্তিক অথেনটিকেশন অ্যালাউ করে। (ব্রুট-ফোর্স অ্যাটাকের সুযোগ তৈরি করে)। |
| `PermitEmptyPasswords yes` | খালি বা এম্পটি পাসওয়ার্ড ব্যবহারের অনুমতি দেয়। |
| `PermitRootLogin yes` | `root` ইউজার হিসেবে লগইন করার অনুমতি দেয়। |
| `Protocol 1` | এনক্রিপশনের একটি আউটডেটেড ভার্সন ব্যবহার করে। |
| `X11Forwarding yes` | GUI অ্যাপ্লিকেশনের জন্য X11 forwarding অ্যালাউ করে। |
| `AllowTcpForwarding yes` | TCP পোর্টের ফরোয়ার্ডিং অ্যালাউ করে। |
| `PermitTunnel` | টানেলিং (tunneling) অ্যালাউ করে। |
| `DebianBanner yes` | লগইন করার সময় একটি নির্দিষ্ট ব্যানার প্রদর্শন করে। |

## Footprinting the Service (সার্ভিস ফুটপ্রিন্টিং)

SSH সার্ভারের ফিঙ্গারপ্রিন্টিং করার জন্য আমরা `ssh-audit` টুল ব্যবহার করতে পারি। এটি ক্লায়েন্ট-সাইড এবং সার্ভার-সাইড কনফিগারেশন চেক করে এবং সার্ভার ও ক্লায়েন্ট কোন কোন এনক্রিপশন অ্যালগরিদম ব্যবহার করছে তা দেখায়।

### SSH-Audit

```bash
00Luffy00@htb[/htb]$ git clone https://github.com/jtesta/ssh-audit.git && cd ssh-audit
00Luffy00@htb[/htb]$ ./ssh-audit.py 10.129.14.132

# general
(gen) banner: SSH-2.0-OpenSSH_8.2p1 Ubuntu-4ubuntu0.3
(gen) software: OpenSSH 8.2p1
...SNIP...

```

আউটপুটের প্রথম কয়েক লাইনে আমরা ব্যানারটি দেখতে পাই, যা OpenSSH সার্ভারের ভার্সন প্রকাশ করে। পুরোনো ভার্সনগুলোতে কিছু ভালনারেবিলিটি ছিল (যেমন: CVE-2020-14145), যা অ্যাটাকারকে MITM অ্যাটাক করার সুযোগ দিত।

### Checking Authentication Methods

আমরা `ssh -v` ব্যবহার করে সার্ভারের সাথে কানেকশন ডিটেইলস এবং অথেনটিকেশন মেথডগুলো দেখতে পারি।

```bash
00Luffy00@htb[/htb]$ ssh -v cry0l1t3@10.129.14.132

...SNIP...
debug1: Authentications that can continue: publickey,password,keyboard-interactive

```

ব্রুট-ফোর্স অ্যাটাকের জন্য আমরা `PreferredAuthentications` অপশন ব্যবহার করে নির্দিষ্ট অথেনটিকেশন মেথড (যেমন পাসওয়ার্ড) সিলেক্ট করে দিতে পারি।

```bash
00Luffy00@htb[/htb]$ ssh -v cry0l1t3@10.129.14.132 -o PreferredAuthentications=password

...SNIP...
debug1: Authentications that can continue: publickey,password,keyboard-interactive
debug1: Next authentication method: password

cry0l1t3@10.129.14.132's password:

```

## Rsync

**Rsync** হলো লোকালি এবং রিমোটলি ফাইল কপি করার জন্য একটি দ্রুত এবং এফিশিয়েন্ট টুল। এটি এর **delta-transfer algorithm**-এর জন্য সুপরিচিত। এই অ্যালগরিদমটি ডেস্টিনেশন হোস্টে ফাইলের কোনো পুরোনো ভার্সন থাকলে, শুধুমাত্র নতুন সোর্স ফাইল এবং পুরোনো ভার্সনের মধ্যকার পার্থক্যগুলো (differences) সেন্ড করে নেটওয়ার্কে ডেটা ট্রান্সমিশনের পরিমাণ কমিয়ে দেয়। এটি প্রায়শই ব্যাকআপ এবং মিররিংয়ের জন্য ব্যবহৃত হয়।

ডিফল্টভাবে এটি **port 873** ব্যবহার করে এবং প্রতিষ্ঠিত SSH সার্ভার কানেকশনের ওপর ভিত্তি করে সিকিউর ফাইল ট্রান্সফারের জন্য কনফিগার করা যায়। যদি পাসওয়ার্ড বা ক্রেডেনশিয়াল জানা থাকে, তবে Rsync ব্যবহার করে টার্গেটের অনেক সংবেদনশীল ফাইল বের করে আনা সম্ভব।

### Scanning for Rsync

```bash
00Luffy00@htb[/htb]$ sudo nmap -sV -p 873 127.0.0.1

Starting Nmap 7.92 ( https://nmap.org ) at 2022-09-19 09:31 EDT
Nmap scan report for localhost (127.0.0.1)
Host is up (0.0058s latency).

PORT    STATE SERVICE VERSION
873/tcp open  rsync   (protocol version 31)

```

### Probing for Accessible Shares

আমরা `nc` বা নেটক্যাট ব্যবহার করে দেখতে পারি কোন শেয়ারগুলোতে আমাদের অ্যাক্সেস আছে।

```bash
00Luffy00@htb[/htb]$ nc -nv 127.0.0.1 873

(UNKNOWN) [127.0.0.1] 873 (rsync) open
@RSYNCD: 31.0
@RSYNCD: 31.0
#list
dev             Dev Tools
@RSYNCD: EXIT

```

### Enumerating an Open Share

ওপরের আউটপুট থেকে আমরা `dev` নামের একটি শেয়ার দেখতে পাচ্ছি, যা আমরা আরও এনুমারেট করতে পারি।

```bash
00Luffy00@htb[/htb]$ rsync -av --list-only rsync://127.0.0.1/dev

receiving incremental file list
drwxr-xr-x             48 2022/09/19 09:43:10 .
-rw-r--r--              0 2022/09/19 09:34:50 build.sh
-rw-r--r--              0 2022/09/19 09:36:02 secrets.yaml
drwx------             54 2022/09/19 09:43:10 .ssh

```

এখানে আমরা `.ssh` ডিরেক্টরি এবং অন্যান্য ইন্টারেস্টিং ফাইল দেখতে পাচ্ছি। আমরা `rsync -av rsync://127.0.0.1/dev` কমান্ডটি ব্যবহার করে সবগুলো ফাইল আমাদের অ্যাটাক হোস্টে সিঙ্ক (sync) করে নিয়ে আসতে পারি। Rsync যদি SSH ব্যবহার করে, তবে আমরা কমান্ডে `-e ssh` ফ্ল্যাগটি যুক্ত করতে পারি।

## R-Services

**R-Services** হলো Unix হোস্টগুলোর মধ্যে TCP/IP-এর ওপর রিমোট অ্যাক্সেস বা কমান্ড এক্সিকিউট করার জন্য তৈরি করা একটি সার্ভিস স্যুট (suite)। SSH আসার আগে এটিই ছিল রিমোট অ্যাক্সেসের ডি ফ্যাক্টো স্ট্যান্ডার্ড (de facto standard)। তবে এতে সিকিউরিটির মারাত্মক ত্রুটি থাকার কারণে এটি বাতিল হয়ে যায়। এটি ক্লায়েন্ট এবং সার্ভারের মধ্যে আনএনক্রিপ্টেড (unencrypted) ফরম্যাটে ডেটা ট্রান্সমিট করে, ফলে অ্যাটাকাররা খুব সহজেই MITM অ্যাটাক করে পাসওয়ার্ড ও লগইন ইনফরমেশন ইন্টারসেপ্ট করতে পারে।

R-services সাধারণত **512, 513, এবং 514** পোর্টে কাজ করে এবং `r-commands` নামের একটি প্রোগ্রামের স্যুট দিয়ে অ্যাক্সেস করা যায়।

### Most Commonly Abused R-commands

| Command | Service Daemon | Port | Transport Protocol | Description (বিবরণ) |
| --- | --- | --- | --- | --- |
| **rcp** | `rshd` | 514 | TCP | লোকাল এবং রিমোট সিস্টেমের মধ্যে দ্বিমুখী (bidirectionally) ফাইল বা ডিরেক্টরি কপি করে। এটি Linux-এর `cp` কমান্ডের মতো কাজ করে কিন্তু ফাইল ওভাররাইট করার সময় কোনো ওয়ার্নিং দেয় না। |
| **rsh** | `rshd` | 514 | TCP | লগইন প্রসিডিউর ছাড়াই রিমোট মেশিনে একটি শেল ওপেন করে। এটি ভ্যালিডেশনের জন্য `/etc/hosts.equiv` এবং `.rhosts` ফাইলের ট্রাস্টেড এন্ট্রিগুলোর ওপর নির্ভর করে। |
| **rexec** | `rexecd` | 512 | TCP | ইউজারকে রিমোট মেশিনে শেল কমান্ড রান করার অনুমতি দেয়। আনএনক্রিপ্টেড নেটওয়ার্ক সকেটের মাধ্যমে ইউজারনেম ও পাসওয়ার্ড দিয়ে অথেনটিকেশনের প্রয়োজন হয়। |
| **rlogin** | `rlogind` | 513 | TCP | ইউজারকে রিমোট হোস্টে লগইন করার অনুমতি দেয়। এটি telnet-এর মতোই কিন্তু শুধু Unix-like হোস্টেই কানেক্ট করতে পারে। |

### Scanning for R-Services

```bash
00Luffy00@htb[/htb]$ sudo nmap -sV -p 512,513,514 10.0.17.2

```

### Access Control & Trusted Relationships

R-services-এর সবচেয়ে বড় সমস্যা হলো এর অ্যাক্সেস কন্ট্রোল। এটি `/etc/hosts.equiv` এবং `.rhosts` ফাইলের ট্রাস্টেড ইনফরমেশনের ওপর নির্ভর করে।

> **Note:** `hosts.equiv` ফাইলটিকে সিস্টেমের সব ইউজারের জন্য গ্লোবাল কনফিগারেশন হিসেবে ধরা হয়, অন্যদিকে `.rhosts` ইউজার-ভিত্তিক (per-user) কনফিগারেশন প্রদান করে।

**Sample .rhosts File:**

```bash
00Luffy00@htb[/htb]$ cat .rhosts

htb-student     10.0.17.5
+               10.0.17.10
+               +

```

এখানে `+` মডিফায়ারটি ওয়াইল্ডকার্ড (wildcard) হিসেবে কাজ করে, অর্থাৎ এটি যেকোনো কিছুকে স্পেসিফাই করতে পারে। ওপরের উদাহরণে, `+` থাকার কারণে যেকোনো এক্সটারনাল ইউজার `10.0.17.10` হোস্ট থেকে `htb-student` অ্যাকাউন্টে রিমোট কমান্ড এক্সিকিউট করতে পারবে।

### Logging in Using Rlogin

এই ভুল কনফিগারেশন কাজে লাগিয়ে আমরা `rlogin` ব্যবহার করে ক্রেডেনশিয়াল ছাড়াই লগইন করতে পারি:

```bash
00Luffy00@htb[/htb]$ rlogin 10.0.17.2 -l htb-student

Last login: Fri Dec  2 16:11:21 from localhost

[htb-student@localhost ~]$

```

### Listing Authenticated Users Using Rwho and Rusers

লগইন করার পর আমরা লোকাল নেটওয়ার্কের সমস্ত ইন্টারঅ্যাক্টিভ সেশনের লিস্ট দেখতে `rwho` এবং আরও বিস্তারিত তথ্যের জন্য `rusers` কমান্ড ব্যবহার করতে পারি।

```bash
00Luffy00@htb[/htb]$ rwho

root     web01:pts/0 Dec  2 21:34
htb-student     workstn01:tty1  Dec  2 19:57  2:25       

```

```bash
00Luffy00@htb[/htb]$ rusers -al 10.0.17.5

htb-student     10.0.17.5:console          Dec 2 19:57     2:25

```

যদিও বর্তমানে SSH-এর কারণে R-services খুব কম ব্যবহৃত হয়, তবুও একজন ওয়েল-রাউন্ডেড (well-rounded) ইনফরমেশন সিকিউরিটি প্রফেশনাল হিসেবে এই পুরোনো প্রোটোকলগুলো সম্পর্কেও আমাদের সম্যক ধারণা থাকতে হবে।
