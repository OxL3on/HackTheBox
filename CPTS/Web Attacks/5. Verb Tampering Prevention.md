# Verb Tampering Prevention - [LINK](https://academy.hackthebox.com/app/module/134/section/1177)


Preventing HTTP Verb Tampering requires consistent authorization configurations at the web server level and consistent HTTP parameter handling at the application code level.

## Patching Insecure Configurations

The core issue across all web servers is using configuration blocks that explicitly name and restrict access for a *specific* HTTP method, leaving all other methods unprotected.

**The Rule:** Never restrict authorization scopes to specific HTTP verbs. Apply authorization rules to the directory/resource as a whole, or use inversion/exclusion keywords to protect everything *except* specific methods. Additionally, unless specifically required, disable the `HEAD` method globally.

**Apache**

* *Vulnerable:* `<Limit GET>`
* *Secure Solution:* Apply restrictions to the entire `<Directory>` block without a `<Limit>` tag. If exceptions are strictly necessary, use `<LimitExcept>`.

```xml
<!-- Secure Apache Configuration -->
<Directory "/var/www/html/admin">
    AuthType Basic
    AuthName "Admin Panel"
    AuthUserFile /etc/apache2/.htpasswd
    Require valid-user
</Directory>

```

**Tomcat**

* *Vulnerable:* `<http-method>GET</http-method>`
* *Secure Solution:* Omit the `<http-method>` tag entirely to apply constraints globally, or use `<http-method-omission>`.

**ASP.NET (IIS)**

* *Vulnerable:* `<allow verbs="GET"...>`
* *Secure Solution:* Remove the `verbs` attribute entirely, or use `add`/`remove` to explicitly manage scopes securely.

## Patching Insecure Coding

Insecure coding occurs due to the inconsistent handling of HTTP parameter arrays (e.g., checking `$_POST` in a security filter, but executing `$_REQUEST` in the final function). Because these functions are often separated across different files in production environments, these inconsistencies are hard to catch during code review.

**The Rule:** Be absolutely consistent. If a function is designed to handle `POST` data, only ever parse `POST` arrays. For universal security filters, always expand the scope of testing to cover *all* request parameters, regardless of the method used.

**Universal Parameter Functions by Language:**
To ensure security filters check all incoming data, use the language's native function for fetching parameters universally:

| Language | Function to cover ALL parameters (GET/POST) |
| --- | --- |
| **PHP** | `$_REQUEST['param']` |
| **Java** | `request.getParameter('param')` |
| **C#** | `Request['param']` |

**Code Example (PHP):**

* **Vulnerable:**
```php
// Checks ONLY POST parameters
if (!preg_match('/[^A-Za-z0-9. _-]/', $_POST['filename'])) {
    // Executes whatever is in the REQUEST (which includes GET parameters)
    system("touch " . $_REQUEST['filename']); 
}

```


* **Secure:**
```php
// Consistently checks and executes using the universal REQUEST array
if (!preg_match('/[^A-Za-z0-9. _-]/', $_REQUEST['filename'])) {
    system("touch " . $_REQUEST['filename']); 
}

```
