# IDOR in Insecure APIs - [LINK](https://academy.hackthebox.com/app/module/134/section/1201)\


Insecure APIs often suffer from IDOR vulnerabilities when they fail to validate if the authenticated user has authorization to access or modify the requested resource. While previous IDOR examples focused on reading files, IDORs in APIs allow you to execute functions (e.g., updating profiles, changing passwords, or escalating privileges) as other users.

**Analyzing the API Request**

When interacting with a profile update feature, intercept the request in a tool like Burp Suite. Pay close attention to the HTTP Method, the API endpoint, the JSON body, and the cookies.

*Example PUT Request:*

```http
PUT /profile/api.php/profile/1 HTTP/1.1
Cookie: role=employee

{
    "uid": 1,
    "uuid": "40f5888b67c748df7efba008e7c2f9d2",
    "role": "employee",
    "full_name": "Amy Lindon",
    "email": "a_lindon@employees.htb",
    "about": "A Release is like a boat."
}

```

**Key Findings:**

1. **Endpoint IDs:** The URL (`/profile/api.php/profile/1`) ends with an ID parameter (`1`).
2. **Hidden JSON Parameters:** The payload contains fields not visible on the front-end HTML form, such as `uid`, `uuid`, and `role`.
3. **Client-Side Authorization:** The `role=employee` cookie suggests the application may be relying on client-side input for authorization—a severe security flaw.

**Exploitation Strategy (Insecure Function Calls)**

To escalate privileges or modify other users, systematically test the API's constraints.

1. **Test ID Mismatch Protections:** Change the JSON `"uid"` to `2`.
* *Result:* The server responds with `uid mismatch`. It validates that the JSON `uid` matches the URL endpoint ID (`/profile/2`).


2. **Test Object Ownership Protections:** Change both the URL to `/profile/2` and the JSON `"uid"` to `2`.
* *Result:* The server responds with `uuid mismatch`. It checks if the `uuid` in the payload belongs to `uid: 2`. Since you used your own `uuid`, the request fails.


3. **Test HTTP Verb Restrictions:** Change the HTTP verb from `PUT` (update) to `POST` (create) or `DELETE` with a new `uid` (e.g., `100`).
* *Result:* The server responds with "Creating new employees is for admins only." It is likely checking the `role=employee` cookie.


4. **Test Parameter Manipulation (Privilege Escalation):** Attempt to change your `"role"` in the JSON payload (and the cookie) to `admin` or `administrator`.
* *Result:* "Invalid role." Unless you know the exact string the backend expects for an administrative role, this fails.



**The Pivot: Information Disclosure**

When active modification (Insecure Function Calls) is blocked by secondary controls (like the `uuid` check), pivot to testing the API for **Information Disclosure**.

Instead of sending a `PUT` request, send a `GET` request to the API endpoint for another user:

```http
GET /profile/api.php/profile/2 HTTP/1.1

```

If the backend lacks access control on `GET` requests, it will return the JSON profile for User 2. This disclosure will leak User 2's `uuid` and their exact `role` designation. You can then use this leaked `uuid` to bypass the `uuid mismatch` protection and successfully modify their account via a `PUT` request, completing the attack chain.
