# Intro to HTTP Verb Tampering - [LINK](https://academy.hackthebox.com/app/module/134/section/1159)


HTTP Verb Tampering exploits insecure web server configurations or flawed application code by sending requests using unexpected HTTP methods to bypass authentication or security filters.

**Common HTTP Verbs**

| Verb | Description |
| --- | --- |
| **HEAD** | Identical to a GET request, but its response only contains headers (no response body). |
| **PUT** | Writes the request payload to the specified location. |
| **DELETE** | Deletes the resource at the specified location. |
| **OPTIONS** | Shows different options accepted by a web server (e.g., accepted HTTP verbs). |
| **PATCH** | Applies partial modifications to the resource at the specified location. |

**Insecure Configurations (Authentication Bypass)**

When an administrator restricts access using specific verbs, they inadvertently leave other verbs unprotected. If a server requires authentication only for `GET` and `POST` requests, an attacker can send a `HEAD` request to access the restricted page without credentials.

```xml
<Limit GET POST>
    Require valid-user
</Limit>

```

**Insecure Coding (Filter Bypass)**

This occurs when developers apply security filters (like sanitization) to a specific HTTP method's variable array (e.g., `$_GET`) but execute the backend function using a generic variable array (e.g., `$_REQUEST`).

```php
$pattern = "/^[A-Za-z\s]+$/";

// The filter only checks the GET parameter
if(preg_match($pattern, $_GET["code"])) {
    // The query executes using $_REQUEST, which includes POST parameters
    $query = "Select * from ports where port_code like '%" . $_REQUEST["code"] . "%'";
    // ...SNIP...
}

```

In this scenario, an attacker can send a malicious payload via a `POST` request. The `$_GET["code"]` remains empty (passing the regex filter), but `$_REQUEST["code"]` processes the malicious `POST` payload, leading to an exploit like SQL Injection.
