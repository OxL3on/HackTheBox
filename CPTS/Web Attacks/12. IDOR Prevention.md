# IDOR Prevention - [LINK](https://academy.hackthebox.com/app/module/134/section/1202)


To effectively eradicate Insecure Direct Object References (IDOR), developers must implement a defense-in-depth approach. Because the root cause of an IDOR is broken access control, simply obfuscating or hiding object IDs is insufficient. Prevention requires a strict two-phased strategy: validating authorization at the object level and securing the references themselves.

## Phase 1: Object-Level Access Control (RBAC)

The foundational fix for IDOR is implementing Role-Based Access Control (RBAC) and mapping it to every single resource in the backend. The server must explicitly allow or deny every request based on the requester's confirmed privileges.

* **Never trust the client:** Do not rely on client-side state (like `role=employee` cookies or hidden JSON parameters) to determine authorization.
* **Session-based validation:** Map the user's secure session token directly to their RBAC profile on the backend.
* **Object-level checks:** Before returning or modifying data, the backend must verify that the authenticated user actually owns the requested object or holds the administrative privileges required to access it.

**Secure Access Control Logic Example:**
This logic ensures an API endpoint only grants read/write access if the user is authenticated AND their internal token ID matches the requested `userId` (or they are an admin).

```javascript
match /api/profile/{userId} {
    allow read, write: if user.isAuth == true
    && (user.uid == userId || user.roles == 'admin');
}

```

## Phase 2: Secure Object Referencing

While robust access control prevents the exploit, secure referencing prevents the initial enumeration. You should implement secure referencing only *after* fixing the access control logic, as strong references alone are just security through obscurity.

* **Eliminate Sequential IDs:** Stop using predictable patterns in URLs and APIs (e.g., `uid=1`, `uid=2`).
* **Implement UUIDv4:** Use cryptographically secure, randomized identifiers for public-facing object references, such as a UUIDv4 (`89c9b29b-d19f-4515-b2dd-abb6e693eb20`).
* **Backend Generation Only:** Never calculate hashes or encoded references on the frontend JavaScript. Generate the UUID on the backend upon object creation, store it in the database, and map it to the internal primary key.

**Backend Reference Mapping Example:**
When a user requests a file, the application accepts the public identifier (which should ideally be a UUID rather than an integer), queries the database mapping, and serves the underlying resource without exposing the true backend file path.

```php
$uid = intval($_REQUEST['uid']);
$query = "SELECT url FROM documents where uid=" . $uid;
$result = mysqli_query($conn, $query);
$row = mysqli_fetch_array($result);
echo "<a href='" . $row['url'] . "' target='_blank'></a>";

```
