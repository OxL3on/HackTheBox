# File Inclusion Prevention - [LINK](https://academy.hackthebox.com/app/module/23/section/622)

To secure applications against file inclusion and directory traversal vulnerabilities, defenders must implement strict input handling, server-level restrictions, and continuous monitoring.

## 1. Secure Coding Practices

The most effective prevention is to **never pass user-controlled input directly into file inclusion functions** (e.g., `include()`, `require()`, `fs.readFile()`).

* **Use Strict Whitelists:** If dynamic loading is required, use an identifier (like an ID or a sanitized string) mapped to a strict whitelist on the backend.
* *Example implementations:* A database table mapping IDs to safe file paths, a hardcoded case-match script, or a static JSON map.
* *Logic:* User inputs `?page=1` -> Backend looks up `1` -> Backend safely includes `about.php`.



## 2. Preventing Directory Traversal

If attackers can traverse directories, they can read sensitive files (like `/etc/passwd`, `tomcat-users.xml`), hijack PHP sessions, or leak source code.

* **Extract Filename Only:** Use native framework tools to strip directory paths from user input.
* *PHP Example:* `basename($input)` will read a provided path and return *only* the filename. (Downside: This breaks functionality if the application legitimately needs to access safe subdirectories).


* **Recursive Sanitization:** If you must sanitize paths manually, ensure it is done recursively to prevent bypasses like `....//`.
* **Code Example (PHP Recursive Sanitization):**
```php
while(substr_count($input, '../', 0)) {
    $input = str_replace('../', '', $input);
};

```

* **Beware of OS Edge Cases:** Relying on custom sanitization or OS-level execution (like `system()`) can lead to bypasses. For example, in a Bash terminal, wildcard patterns like `cat .?/.*/.?/etc/passwd` can evaluate to `../../etc/passwd`, bypassing simple `../` string filters.

## 3. Web Server & Environment Configuration

Applying defense-in-depth configurations restricts the impact even if an inclusion vulnerability exists.

* **Disable Remote File Inclusion:** Ensure the server cannot fetch remote URLs by default.
* *PHP (`php.ini`):*
```ini
allow_url_fopen = Off
allow_url_include = Off

```


* **Lock to the Web Root:** Prevent the application from reading files outside its designated directory.
* *Containerization:* Run the application within a Docker container to isolate its filesystem.
* *PHP (`php.ini`):*
```ini
open_basedir = /var/www

```


* **Disable Dangerous Modules:** Ensure modules like the PHP `Expect` module or Apache's `mod_userdir` are disabled if not strictly required.

## 4. Web Application Firewall (WAF)

Deploy a WAF (like **ModSecurity**) to provide an exterior shell of defense and monitor for attacks.

* **Permissive Mode:** When first deploying a WAF, run it in "permissive mode." It will log/report requests it *would* have blocked without actually dropping them. This allows defenders to tune rules and eliminate false positives before enforcing blocking mode.
* **Visibility:** Even if an exploit (like a zero-day) works, a hardened system and WAF will generate unique logs, giving defenders a better chance to detect the breach early.
