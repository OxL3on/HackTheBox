PHP is the dominant server-side scripting language, powering nearly 80% of the web. When you identify a target running PHP (e.g., pages ending in `.php`), any file upload vulnerabilities present a prime opportunity to drop a PHP-based web shell for Remote Code Execution (RCE).

Here is your quick-reference guide for bypassing file upload restrictions to deploy a PHP web shell.

## The Attack Workflow: Bypassing File Restrictions

Web applications often restrict file uploads (like profile pictures or vendor logos) to specific image formats (`.png`, `.jpg`, `.gif`). You can bypass these client-side or basic server-side filters by manipulating the HTTP headers in transit.

1. **Prepare the Payload:** Obtain a PHP web shell (like [WhiteWinterWolf's](https://github.com/WhiteWinterWolf/wwwolf-php-webshell)). Strip out any obvious author comments or ASCII art to avoid basic signature detection. Save it as `shell.php`.
2. **Configure the Proxy:** Route your web browser's traffic through a proxy tool like Burp Suite (typically `127.0.0.1:8080`).
3. **Initiate the Upload:** Attempt to upload your `shell.php` file via the target's web form and hit submit.
4. **Intercept & Modify (The Bypass):** * In Burp Suite, catch the outbound HTTP `POST` request.
* Locate the `Content-Type` header associated with your file payload.
* Change it from `application/x-php` to a permitted image MIME type, such as `image/gif` or `image/jpeg`.


5. **Forward the Request:** Send the modified packet to the server. The server reads the manipulated `Content-Type`, assumes it is a safe image, and saves the `.php` file to disk.

## Execution

To execute the payload, you must locate where the server stores uploaded files. Navigate directly to that URL in your browser (e.g., `http://target.com/images/vendor/shell.php`). The backend will process the PHP code, presenting you with an in-browser interface to execute underlying OS commands.

## Operational Considerations (OpSec)

Web shells are a means to an end, not a permanent solution. Keep these limitations in mind during an engagement:

* **Volatility:** Many web servers run cleanup scripts that automatically delete uploaded files after a set period.
* **Limited Interactivity:** You cannot easily chain commands (e.g., `whoami && id`), use interactive prompts, or easily navigate the file system.
* **Forensic Footprint:** Leaving web shells on a client's server is noisy and leaves blatant artifacts for defenders.

**Best Practice:** Always use the web shell strictly as a stepping stone. Use it to execute a payload that catches a stable, interactive **reverse shell** back to your attack machine, and then immediately delete the web shell file from the target's webroot to cover your tracks. Document the exact file names, paths, and file hashes (MD5/SHA1) of your uploads for the client report.
