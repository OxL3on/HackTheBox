# Introduction to Web Shells - [LINK](https://academy.hackthebox.com/app/module/115/section/1119)

A **web shell** is a malicious script uploaded to a web server that grants an attacker Remote Code Execution (RCE) capabilities directly through a web browser. Because modern external perimeters are heavily hardened, web application vulnerabilities are often the primary vector for gaining an initial foothold into an internal network.

**Common Attack Vectors for Uploading Web Shells**

* **Unrestricted File Uploads:** Bypassing client-side or server-side checks on public forms (e.g., resumes) or authenticated portals (e.g., user profile picture uploads).
* **Application Deployment Features:** Uploading malicious `.war` files into administrative interfaces like Apache Tomcat, Axis2, or Oracle WebLogic.
* **Misconfigurations:** Exploiting insecure FTP services that allow uploading files directly into the server's webroot directory.

**Web Shell Payload Languages**
The payload must match the backend environment and language supported by the target web server:

* **PHP:** (`.php`) Common on Apache/Nginx servers.
* **JSP:** (`.jsp`, `.war`) Common on Java-based servers like Tomcat.
* **ASP.NET:** (`.aspx`) Common on Windows IIS servers.

**Operational Limitations & Strategy**

* **Instability:** Web shells operate via stateless HTTP requests, meaning they are non-interactive and can be highly unreliable for complex tasks.
* **Volatility:** Many modern web applications, load balancers, or security controls automatically purge uploaded files after a short period.
* **The Core Strategy:** Never rely on a web shell for long-term access. Use the web shell's initial RCE solely as a stepping stone to execute a payload that establishes a stable, interactive **reverse shell** back to your attack machine.
